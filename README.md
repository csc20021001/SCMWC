# SCMWC

> If you have to keep watching it, let us watch it for you.

框住螢幕上任何一塊區域，它變了就通知你。不管那塊區域屬於哪個程式 ——
Citrix、SAP、2005 年寫的內部 ERP、Chrome、交易軟體都一樣，因為只看 pixels，
不需要任何整合。

## 現在能做什麼（v0，已驗證可運作）

- 開啟程式就是主視窗，最上面一顆「選取想要監視的區域」
- 兩種選法：**拖曳** = 自訂區域；**點一下** = 選取整個視窗
  （游標移動時會即時highlight底下的視窗並顯示它的標題與尺寸）
- 選取畫面右上角有 **✕ 取消鈕**，也可以按 Esc
- **可以同時監視多個區域**，每一項各自有自己的通知條件與檢查頻率
- 停掉某一項：點清單那一列右邊的 **✕**，或點浮在被監視區域旁邊的 **✕**
- 雙擊清單某一列可以改它的通知條件
- 也常駐在系統匣，主視窗關掉只是收起來，監視繼續跑
- **通知紀錄**面板：每次條件成立都會記一筆。這是用來分辨
  「條件根本沒成立」和「成立了但 Windows 沒把通知顯示出來」——
  沒有這個面板，這兩種情況對使用者來說長得一模一樣
- **測試通知**按鈕：不經過任何條件，直接走完整條通知路徑（音效 + 氣泡 + Discord）

沒有畫面預覽：那塊東西只是好看，而且為了它每秒要多做 20 張沒人看的點陣圖。
只有在真的要附加到 Discord 時才會產生截圖。

### 四種通知條件

| 使用者看到的選項 | 判斷方式 | 觸發方式 |
| --- | --- | --- |
| 畫面只要有變化就通知我 | 64x64 灰階網格的平均絕對差超過門檻 | 每次超過都通知（有冷卻時間） |
| 跑完了才通知我 | 進度條填到 ≥99% | **邊緣觸發**，跑完才響一次 |
| 跑到指定進度就通知我 | 進度條填到 ≥ 指定 % | **邊緣觸發** |
| 顏色變了就通知我 | 區域平均色與基準色的 RGB 距離超過容許值 | **邊緣觸發**，雙向都算 |

邊緣觸發是刻意的：條件從不成立變成成立的那一刻才通知一次，之後要等條件重新
不成立才會再武裝。不然進度條停在 100% 會每秒吵一次。

### 設定畫面不放裸數字

使用者不需要知道「64x64 灰階網格的平均絕對差」是什麼。設定畫面只問他聽得懂的問題：

| 使用者看到 | 實際對應 |
| --- | --- |
| 要多小的變化才算變化：一點點就通知 / 普通 / 只有明顯變化才通知 | 建立監視時量到的雜訊底線 × 1.5 / 3 / 8 |
| 顏色要差多少才算變了：稍微不同就算 / 明顯不同才算 / 差很多才算 | RGB 距離 25 / 45 / 90 |
| 多久看一次畫面：盯緊 / 常常看 / 普通 / 偶爾看 | 每秒 20 / 5 / 1 次、每 3 秒 1 次 |

靈敏度刻意做成「相對於這個目標的雜訊底線」而不是絕對數字 ——
同一個絕對門檻在不同目標上的意義完全不同。

清單裡的狀態也不寫 Live / Blind，而是「監視中 / 看不到畫面 / 已收到背景 / 視窗已關閉」。

### 進度條怎麼量

**框選範圍不必剛好等於進度條**。使用者最自然的操作是「點一下選整個視窗」，
所以程式會自己在框選範圍裡找出那條進度條：掃描 96 條橫帶，找出被切成
左右兩塊、各自內部顏色一致、兩塊顏色差很多的那一條。

找到之後才學「填滿色」與「未填色」，再數從左邊起連續有幾欄接近填滿色。
還沒找到時回報「學習中」；連續找不到就會**主動跳警告**說這塊範圍裡沒有進度條，
而不是安靜地永遠不通知。

兩個必要的細節：

- **最外側 3 欄不算**。真實的進度條左右都有邊框或圓角，拿最外側那欄當參考色會
  全部算錯 —— 這會讓量到的最大值卡在 80% 上不去。
- **挑橫帶不能只看顏色對比**。按鈕邊框那種高對比細線會贏過進度條。
  真正的判準是「上下相鄰的橫帶在同一個位置也有分界線」，因為進度條是有厚度的。
- **呼應度不足的候選一律不接受**，寧可這次找不到、下次再找。
  只要將就一次就會鎖在錯的位置上永遠量錯 —— 實測看過鎖到呼應度 0 的細線，
  結果 20 秒內一次都不通知。
- **會自我糾正**：如果畫面明明一直在變、量到的進度卻長時間紋風不動，
  就重新找一次橫帶。

實測三種框選方式（整個視窗 / 只框進度條 / 框下半部）現在都能正確找到進度條、
量到 100%、正常觸發。

### 抓取頻率

實測（`--bench`）：

| 階段 | 耗時 |
| --- | --- |
| `PrintWindow` | 20~24 ms（跟視窗大小幾乎無關） |
| 讀回像素 | 0.2~1.6 ms |
| 分析 | 0.1 ms |

所以單項的硬體上限是 **40~50 Hz**。最快的設定是每秒 20 次，實測達到 19.8 次/秒。
三項同時用最快設定會掉到每項 13 次/秒 —— `PrintWindow` 是序列化的，這是硬限制。

兩件為了真的跑到這個速度而必須做的事：

- **取樣搬到背景執行緒**。一次 20ms 放在 UI 執行緒上，頻率一高介面就卡死。
  取樣執行緒只把結果排進佇列，通知、預覽、清單更新全部留在 UI 執行緒做。
- **睡到「下一項該取樣」為止，而不是固定睡 15ms**。Windows 的計時器精度預設是
  15.6ms，固定睡 15ms 會讓「每 50ms 一次」變成「每 60ms 一次」，頻率直接少四分之一
  （實測 16.4 次/秒）。改成算出剩餘時間再睡之後是 19.8 次/秒。

### 「跑完了」不要求剛好 100%

門檻設在 **96%**。真實的進度條有邊框或圓角，量到滿的時候往往只有 96~98%，
卡在 99 就永遠不會通知。

### 「滿了一瞬間就歸零」怎麼處理

真實的工作視窗常常是跑到滿**立刻歸零重跑**，那個瞬間可能根本不會被取樣到。
所以除了「量到 ≥ 目標」之外，還會從**進度大幅倒退**推斷：
上次看到 80%、這次只有 5%，那中間一定跑完過。通知會誠實寫出是這樣推斷的
（「在兩次檢查之間完成，進度已從 80% 歸零重跑」）。

代價是誤判：如果那條進度條是失敗重試而不是跑完，也會被當成跑完。

**而且這條路徑不是備案，是必需品。** Windows 的進度條控制項填充時是有動畫的，
所以數值瞬間歸零的目標，畫面上**根本不會出現滿的那一格** ——
實測用每秒 20 次去盯一個 5 秒跑完就歸零的進度條，最高只量得到 92%，
再快也沒用。這種目標只能靠推斷，而推斷每一輪都準確觸發一次。

會停留在完成狀態的進度條則量得到 100%，通知會直接寫「跑完了（98%）」。

### 推播到 Discord

在 Discord 頻道設定 → 整合 → Webhook 建一個，把網址貼進「Discord 推播設定」。
之後通知會同時推到那個頻道，手機就收得到 —— 電腦在跑東西時可以先去吃飯。

附上截圖的選項**預設關閉**：那等於把螢幕內容上傳到外部服務，必須由使用者自己打開。
每一項監視也可以各自決定要不要推播。
- 背景每 0.5 秒取樣，畫面差異超過門檻就通知（音效 + 氣泡通知）
- 建立監視時自動量一次雜訊，據此設門檻，避免游標閃爍造成假警報
- 狀態視窗顯示每項監視的差異值、狀態、**覆蓋率**，以及最後一次變化的畫面
- 目標視窗被最小化時自動改成停在螢幕外繼續監視
- 若偵測到目標隱藏後自己停止繪製，自動把它放回螢幕上並說明原因

## 測試目標：ProgressDemo.exe

`bin\ProgressDemo.exe` 是拿來測 SCMWC 的假工作視窗，會跑進度條。
刻意做出三種不同性質的變化，方便測不同條件：

| 元素 | 變化性質 | 用來測 |
| --- | --- | --- |
| 進度條 | 持續小幅變化 | 一般的變化偵測 |
| 百分比數字 | 小面積文字變化 | 最難偵測的那種，適合調門檻 |
| 完成時整條橫幅變綠 + 文字變 Completed | 大面積劇烈變化 | 一定要抓到的事件 |

速度可選 30 / 12 / 5 秒跑完，跑到 100% 會停在 Completed 五秒再重來。
勾「跑完立刻歸零（不停留）」可以重現真實工作視窗那種「滿了一瞬間就重跑」的行為 ——
那是最容易讓監視工具漏掉通知的情況。
命令列參數 `--fast --nohold` 可以直接開在那個組合，給自動測試用。

## 已驗證

`SCMWC.exe --selftest "視窗標題片段"` 會不經過 UI，直接拿產品的
`Capturer` + `Watch` 去盯一個真實視窗 20 次，結果寫進 `bin\selftest.log`
並存一張 `bin\selftest-shot.png`。

對硬體合成的 Chromium 視窗（含 WebGL canvas）實測：19 次觸發、
覆蓋率 100%、零盲區、框選區域對位正確。

其他測試入口，全部不需要動滑鼠：

- `--triggertest "標題"` 依序驗證四種通知條件。對 ProgressDemo 實測結果：
  AnyChange 52 次、Full 2 次（35 秒內剛好 2 個循環，證明邊緣觸發有效）、
  到 50% 觸發 3 次、變色觸發 4 次並正確認出 RGB(205,79,79)→RGB(64,170,109)。
- `--bartest "標題"` 用三種框選方式（整個視窗 / 只框進度條 / 框下半部）各跑一輪，
  回報每種方式量得到幾次進度、最高量到幾 %、觸發幾次、以及自動找到的進度條位置。
  這個測試就是抓出「選整個視窗永遠不會通知」的那一個。
- `--misstest "標題"` 迴歸測試「滿了立刻歸零會不會漏掉通知」。刻意用最糟的組合：
  進度條 5 秒跑完就歸零、監視每 3 秒才看一次。實測 45 秒觸發 7 次，
  而且每次的原因都顯示上次看到的是 78~93%，**從來沒看到 100%** ——
  證明推斷路徑有效。修好之前這個數字是 0。
- `--uitest "標題"` 驗證「點某一列的叉叉就移除」，走的是跟真實滑鼠相同的命中判定。
  同時放兩項監視，順便驗證多項並存。
- `--settingsui "標題" [毫秒]` 把設定畫面秀出來幾秒後自動關閉，用來目視檢查版面。
- `--bench "標題1|標題2"` 量 `PrintWindow` / 讀像素 / 分析各花多少毫秒，算出頻率上限。
- `--ratetest "標題"` 量**實際達到**的取樣頻率（不是設定值），並比較 1 項與 3 項並存。
- `--trace "標題"` 逐筆記錄每次取樣量到的進度值。要查「為什麼沒通知」就用這個 ——
  上面那些「最高只到 92%」「鎖到錯的橫帶」都是用它看出來的。
- `--discordtest <url> [img]` 送一則測試推播。可以指向本機 HTTP 伺服器驗證封包格式，
  不需要真的 webhook。
- `--pick x,y` 印出某座標會選到哪個視窗，驗證 z 序與 cloaked 過濾。

### 移除監視為什麼不做成「選取 + 按鈕」

原本是「選一列 → 按『移除選取的監視』」，但它會按了沒反應。
第一個原因是主視窗每 500ms 重建整個清單，而且在 `BeginUpdate()`/`EndUpdate()`
**內部**設定 `SelectedIndex` —— 在 update 模式中設選取項目不可靠，會被吃掉。
修掉之後在真實環境還是不穩定。

結論是這個互動本身就不該依賴選取狀態：現在每一列右邊自己有一個叉叉，
被監視的區域旁邊也浮著一個，兩者都不需要先選取任何東西。

## 三個從探針帶過來的硬性設計決定

這些不是風格選擇，是 `H:\screenwatch-probe\` 實測出來的結果。

**1. `PrintWindow` 一定要帶 `PW_RENDERFULLCONTENT`。**
不帶 flag 抓 Chromium / Electron 是 100% 黑畫面。從螢幕 `BitBlt` 則是視窗一被
遮住就完全失效。所以抓法只有一個選擇。

**2. 使用者框的座標和 `PrintWindow` 交回的影像不是同一個座標系。**
DPI-unaware 的目標（SAP、老 ERP）交回來的影像比視窗小，比例是
`視窗DPI / 螢幕DPI`。抓取前先把畫布塗成哨兵洋紅，就能從「實際被畫到的範圍」
自動校正，見 `Capturer.PaintedBounds` 和 `Watch.MapRegion`。

**3. 判斷鎖定狀態不能看輸入桌面名稱。**
Win10/11 的鎖定畫面是 `LockApp.exe`，跑在 **Default 桌面**上，
用 `OpenInputDesktop` 判斷會全程回報「沒鎖」。要用
`WTSQuerySessionInformation` 的 `SessionFlags`，見 `Native.IsSessionLocked`。
（好消息是鎖定並不影響抓取，所以這只用在狀態顯示。）

## 兩條不准違反的產品原則

**不把技術限制推給使用者。**
最小化的視窗確實抓不到，但正確做法不是跳一個「請不要最小化」的提示，
而是攔下 `EVENT_SYSTEM_MINIMIZESTART`、把視窗停到螢幕外繼續監視。
使用者體感一樣是收起來了。

**不准靜默失效。**
抓到黑畫面或什麼都沒抓到時，狀態必須是 `Blind`，而且那段時間要從覆蓋率裡扣掉。
使用者有權知道哪段時間我們其實沒在看。`Sample.IsUsable` 就是這道閘門 ——
無效的畫面不會被拿去比較，也不會被當成「沒有變化」。

## 架構

```
SCMWC.exe（系統匣程式，單一檔案）
│
├─ TrayApp          系統匣圖示、選單、UI 計時器、通知佇列的消費端
│   ├─ 取樣執行緒     背景執行緒，唯一會呼叫 PrintWindow 的地方
│   └─ 通知佇列       取樣執行緒只排隊，UI 執行緒才真的發通知
│
├─ MainForm         主視窗：新增監視、清單、通知紀錄
├─ RegionSelector   全螢幕遮罩，拖曳框選 / 點選整個視窗
├─ WatchSettingsForm 通知條件設定
├─ Badge            浮在被監視區域旁邊的 ✕
│
├─ Watch            一個監視項目：目標視窗、區域、間隔、狀態、覆蓋率
│   ├─ Capturer     PrintWindow + GetDIBits，哨兵色偵測未繪製
│   └─ Trigger      四種通知條件、進度條定位與量測
│
├─ Discord          webhook 推播（背景執行緒送出）
└─ Config           %LOCALAPPDATA%\SCMWC\config.txt
```

資料流：**取樣執行緒** → `Watch.Tick()` → `Capturer.Grab()` 抓整個視窗 →
`Trigger.Evaluate()` 判斷條件 → 成立就排進佇列 → **UI 執行緒**每 100ms 取出 →
音效 + 氣泡通知 + 通知紀錄 + Discord。

執行緒規則只有一條：**只有取樣執行緒碰 GDI，只有 UI 執行緒碰視窗**。

## 建置與打包

不需要安裝任何 SDK，用 Windows 內建的 .NET Framework 編譯器：

```powershell
H:\SCMWC\build.ps1
```

產出：

| 檔案 | 說明 |
| --- | --- |
| `bin\SCMWC.exe` | 主程式，約 60 KB |
| `bin\ProgressDemo.exe` | 測試用進度條視窗 |
| `dist\SCMWC-Setup.exe` | **安裝包**，約 114 KB，上面兩個和文件都內嵌在裡面 |

安裝程式會先顯示完整的使用條款與免責聲明，**勾選同意之前「安裝」按鈕是停用的**。
安裝到 `%LOCALAPPDATA%\Programs\SCMWC`（不需要系統管理員權限），
建立開始功能表與桌面捷徑，寫入「應用程式與功能」的解除安裝項目，
並記錄同意條款的版本與時間到 `accepted-eula.txt`。

解除安裝會一併刪除設定檔（裡面有 Discord webhook 網址）。

## 程式碼簽章

沒簽章的安裝檔會被 SmartScreen 擋下，這是發佈前的硬性前置條件。

```powershell
# 1. 先簽兩個內層 exe
.\sign.ps1 -Thumbprint <憑證指紋> -Files bin\SCMWC.exe, bin\ProgressDemo.exe

# 2. 重新打包（安裝程式會把已簽章的 exe 內嵌進去）
.\build.ps1

# 3. 再簽安裝程式本身
.\sign.ps1 -Thumbprint <憑證指紋> -Files dist\SCMWC-Setup.exe
```

順序不能顛倒：安裝程式把兩個 exe 當資源內嵌，先簽安裝程式的話裡面裝的還是未簽章的版本。

`sign.ps1` 用 Windows 內建的 `Set-AuthenticodeSignature`，**不需要 Windows SDK**。
它一律加上 RFC3161 時間戳記 —— 沒有時間戳記的話，憑證到期當天所有已發佈的簽章
就會同時失效；有的話簽章在憑證到期後仍然有效。

查憑證指紋：

```powershell
Get-ChildItem Cert:\CurrentUser\My | Format-List Subject, Thumbprint, NotAfter
```
